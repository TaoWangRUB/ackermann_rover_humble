# ADR-009 — Force `Grid/Sensor=1` (camera/cloud) for RTAB-Map's occupancy grid

**Status:** accepted
**Date:** 2026-05-02
**Component:** `rtabmap_bringup` (launch)

## Context

RTAB-Map's occupancy grid (`/map`) was rendering the explored free-space as a
**flat-topped triangular wedge** (the perpendicular-Z projection of the camera
FOV cone) instead of the expected **circular sector** (`x² + y² ≤ R²`) bounded
by the radial sensing range.

We confirmed by binary-bisecting commits on the SLAM stack that the breaking
change is **`7eb283c` "Wire /scan to RTAB-Map and fix loop-closure
registration"**, which flipped `subscribe_scan` from conditional (only when
`vision=false`, i.e. ICP-odom mode) to unconditionally `True`. The previous
commit (`e7ac530`) produced the correct sector shape (numerically verified:
max radial ≈ 5.16 m, lateral/forward ratio ≈ 0.627 ≈ sin 40°).

## Why `subscribe_scan=True` broke the shape (RTAB-Map source)

In [`rtabmap_ros/rtabmap_slam/src/CoreWrapper.cpp:459-479`](https://github.com/introlab/rtabmap_ros/blob/jazzy-devel/rtabmap_slam/src/CoreWrapper.cpp#L459-L479)
the wrapper auto-overrides two grid parameters when the user subscribes to
`/scan` *without* explicitly setting them:

```cpp
int gridSensor = Parameters::defaultGridSensor();  // = 1 (camera/cloud)
if((this->isSubscribedToScan2d() || ...) &&
   parameters_.find(Parameters::kGridSensor()) == parameters_.end())
{
    parameters_.insert(ParametersPair(Parameters::kGridSensor(), "0"));   // → laser scan
}
if((this->isSubscribedToScan2d() || ...) &&
   parameters_.find(Parameters::kGridRangeMax()) == parameters_.end() &&
   gridSensor == 0)
{
    parameters_.insert(ParametersPair(Parameters::kGridRangeMax(), "0"));  // → no limit
}
```

So `subscribe_scan=True` silently flips:
- `Grid/Sensor`: `1` (camera/cloud) → **`0`** (laser scan)
- `Grid/RangeMax`: `5.0` (default) → **`0`** (no limit)

The 2D laser scan path in [`LocalGridMaker.cpp:198`](https://github.com/introlab/rtabmap/blob/0.22.1/corelib/src/LocalGridMaker.cpp#L198)
projects each scan ray onto the ground plane using the LaserScan's range field
directly. When `/scan` is generated by `depthimage_to_laserscan`, that range
field carries the camera's **perpendicular-Z** depth (not the radial distance)
— so the cleared cells trace out a triangle bounded by the perpendicular plane
at `z = max(depth)`, not a circle of radius R.

By contrast, the camera/cloud path (`Grid/Sensor=1`) builds a 3D point cloud
from the depth image, segments it into ground/obstacle, then raytraces from
camera origin to each cloud point in true 3D. A radially-bounded cloud
projects to a circular sector on the ground plane.

## Decision

In [`src/rtabmap_bringup/launch/rtabmap_slam.launch.py`](../../src/rtabmap_bringup/launch/rtabmap_slam.launch.py),
pin **`Grid/Sensor='1'`** explicitly in the `rtabmap_parameters` dict so
CoreWrapper's auto-override condition (`parameters_.find(...) ==
parameters_.end()`) is bypassed:

```python
rtabmap_parameters = {
    ...
    'Grid/Sensor': '1',      # camera/cloud — never let CoreWrapper auto-flip to scan
    ...
}
```

**`Grid/RangeMax` is intentionally not set** — the second auto-override block
at CoreWrapper.cpp:472-479 is itself gated on `gridSensor==0`, so once
`Grid/Sensor=1` is pinned the RangeMax auto-override never fires and the
parameter keeps its default `5.0` m. Verified at runtime: `ros2 param get
/rtabmap Grid/RangeMax` returns `String value is: 5.0`.

`subscribe_scan=True` is **kept** — `/scan` is still consumed by RTAB-Map for
loop-closure verification under `Reg/Strategy=2` (Vis+ICP cascade), where it
provides the second-stage geometric check after visual matching. Only the
*occupancy grid* sensor source is forced to camera/cloud.

## Consequences

- `/map` reverts to the radial sector shape bounded by `Grid/RangeMax = 5 m`.
- Loop closure robustness is unaffected — Reg/Strategy=2 cascade still uses scan.
- Anyone tuning `Grid/Sensor` later **must keep it explicitly set**; removing
  the explicit value re-triggers the auto-flip if `subscribe_scan` is true.
- Hardware path (real lidar) behaviour is unchanged — Grid/Sensor=1 still uses
  the depth camera path; the lidar contributes only to scan-based loop verify
  via Reg/Strategy=2.

## How RTAB-Map's `/map` is actually built (for future maintainers)

The `/map` topic is **not** the union of frames as they arrive. It's a
re-stitching every time the pose graph changes:

1. **Per-keyframe local grid**: every accepted keyframe gets a
   `Signature` containing a *local* occupancy grid built once by
   [`LocalGridMaker::createLocalMap`](https://github.com/introlab/rtabmap/blob/0.22.1/corelib/src/LocalGridMaker.cpp#L188).
   The sensor source is `Grid/Sensor`. The local grid is cached on the
   signature and never rebuilt (unless the DB is reloaded).

2. **Global stitching**: whenever a keyframe is added or a loop closure is
   accepted (which optimises the graph), [`MapsManager`](https://github.com/introlab/rtabmap_ros/blob/jazzy-devel/rtabmap_util/src/MapsManager.cpp)
   re-renders `/map` by placing each cached local grid at its node's
   *current* (post-optimisation) pose and merging cell values
   (occupied > free > unknown). Publish cadence is gated by
   `Rtabmap/DetectionRate` (1 Hz in our config).

So map *shape* is fixed by `LocalGridMaker` at keyframe-add time. Loop closures
re-place those local grids but never reshape them. This is why the
`Grid/Sensor` choice has to be right at *node creation*, not later.
